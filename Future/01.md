# Future Idea #01 - Deployment & FTP

**Status:** ✓ Idea documented  
**Area:** Deployment / Developer Experience  
**Type:** Future Feature

---

## The Idea

One of the longer-term ideas for WAMP-DS is to allow developers to deploy their projects directly from the application.

At the moment, WAMP-DS is primarily focused on the local development environment:

    Create Project
        ↓
    Write Code
        ↓
    Run Locally
        ↓
    Preview
        ↓
    Test

A natural extension of that workflow would be:

    Create Project
        ↓
    Write Code
        ↓
    Run Locally
        ↓
    Preview
        ↓
    Test
        ↓
    Deploy

The idea is to eventually make that final step possible without requiring the developer to leave WAMP-DS and open a separate FTP client.

---

## FTP Support

The most obvious starting point would be FTP deployment.

A project could contain deployment information such as:

- Server hostname
- Port
- Username
- Password
- Remote directory
- Passive or active transfer mode
- Files or directories to exclude

The developer could then deploy the project directly from WAMP-DS.

The goal would not be to reinvent FTP.

There are already excellent tools dedicated to file transfer.

The purpose would instead be to remove the need to leave the development environment for a common part of the development workflow.

---

## SFTP

SFTP should also be considered alongside traditional FTP.

Where supported by a hosting provider, SFTP would provide encrypted file transfer and could become the preferred deployment method.

Potential authentication options could eventually include:

- Username and password
- SSH keys
- Other supported authentication mechanisms

The exact implementation would be determined if and when the feature moves from an idea into development.

---

## Deployment Profiles

A particularly useful extension would be deployment profiles.

A project might have several environments:

    Development
    Staging
    Production

Each could have its own deployment configuration.

For example:

```text
Development
    Server: dev.example.com
    Remote Path: /www/project-dev

Staging
    Server: staging.example.com
    Remote Path: /www/project-stage

Production
    Server: example.com
    Remote Path: /www/project
```

This would allow the developer to select the intended destination rather than repeatedly entering connection details.

It would also provide a foundation for more advanced deployment functionality later.

---

## Manual Deployment

The initial implementation should probably focus on explicit deployment.

Something as simple as:

    Project
        ↓
    Deploy
        ↓
    Select Deployment Profile
        ↓
    Confirm
        ↓
    Upload

would provide a useful starting point.

The developer remains in control of when files are uploaded.

This is important because deployment is fundamentally different from local preview.

A local preview can be refreshed constantly.

A production deployment can have consequences.

---

## Possible Future Automation

Once a reliable manual deployment system existed, more advanced options could potentially be considered.

For example:

- Deploy changed files only
- Upload automatically after saving
- Watch a project for changes
- Deploy only selected directories
- Exclude development files
- Compare local and remote files
- Show deployment progress
- Show files that will be uploaded before deployment
- Maintain deployment history
- Roll back a deployment

These are possibilities rather than requirements.

The simplest useful deployment system should come first if this idea is ever implemented.

---

## Safety And Control

Automatic deployment would need particular care.

A developer could easily be working on a production profile while expecting to be working on a development server.

For that reason, automatic deployment should not be assumed to be part of the initial feature.

A future implementation could require explicit confirmation before deploying to a production environment.

For example:

    Deploy
        ↓
    Production
        ↓
    Confirm Destination
        ↓
    Upload

The exact user interface would be determined during implementation.

The important principle is that WAMP-DS should make deployment easier without making accidental deployment easier.

---

## Why It Fits WAMP-DS

Deployment is a natural extension of the direction WAMP-DS is already taking.

The application is increasingly becoming more than a collection of local development tools.

It is intended to bring together the things a web developer repeatedly needs:

    Project Management
          ↓
    Code Editing
          ↓
    Apache / PHP
          ↓
    MySQL
          ↓
    SSL
          ↓
    Live Preview
          ↓
    Development
          ↓
    Deployment

Adding deployment would extend that workflow beyond the local machine.

It would allow WAMP-DS to become part of the process from the moment a project is created through to the point where that project is published.

---

## Not A Commitment

This entry is an idea, not a development commitment.

There are many questions that would need to be answered before implementation:

- Which FTP/SFTP library should be used?
- How should credentials be stored?
- How should deployment profiles be represented?
- Should deployment be project-specific?
- How should remote file conflicts be handled?
- Should only changed files be uploaded?
- How should production deployment be protected?
- Should deployment support multiple hosting providers?
- Should deployment eventually integrate with cloud APIs?

None of these decisions need to be made yet.

The purpose of documenting the idea now is simply to preserve the concept and establish the direction it could take if it becomes a priority.

---

## The Bigger Picture

WAMP-DS is being developed through real-world use.

That means future ideas are likely to come from the same place as many of the current features:

> "I'm doing this again. There must be a better way."

Deployment is one of those natural next steps.

If WAMP-DS can create the project, provide the runtime, edit the code, run the server, manage the database, handle SSL and show the live result, eventually being able to publish that project from the same environment makes sense.

Whether that becomes part of WAMP-DS remains to be seen.

For now, the idea is recorded.
