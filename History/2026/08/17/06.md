# Development Entry #06 - Preview Cache Refresh

**Date:** 17 August 2026  
**Area:** Live Preview / Developer Experience  
**Type:** Bug Fix / Enhancement  
**Status:** Complete

---

## The Problem

While continuing real-world development inside WAMP-DS, another small but frustrating issue appeared during normal use.

Changes made to CSS files were not always appearing immediately in the live preview.

The file was being saved correctly.

The preview was being refreshed.

But the visual result could still show the previous version of the stylesheet.

This was particularly noticeable when making small styling changes and repeatedly saving the file to check the result.

The development workflow became:

    Edit CSS
        ↓
    Save
        ↓
    Preview Refreshes
        ↓
    Changes Still Not Visible
        ↓
    Wonder What Broke

The problem wasn't that WAMP-DS had failed to save the file.

The problem was that the preview was still using cached resources.

---

## The Existing Preview Refresh

WAMP-DS uses WebView2 for its embedded previews.

The existing refresh implementation was straightforward:

```csharp
public void RefreshPreview()
{
    if (Browser.CoreWebView2 != null)
    {
        Browser.Reload();
    }
}
```

The docked preview used the same approach:

```csharp
private void RefreshDockedPreview()
{
    if (LivePreviewBrowser.CoreWebView2 != null)
    {
        ClearOutput();
        LivePreviewBrowser.Reload();
    }
}
```

At first glance, this appears to be exactly what is required.

The page reloads.

The server is still running.

The browser requests the page again.

However, a normal browser reload does not necessarily mean that every resource is fetched again from the server.

CSS, JavaScript, images and other resources can still be satisfied from the browser cache.

---

## Identifying the Cause

The issue became much clearer once the preview refresh itself was examined.

The problem wasn't with the PHP preview server.

It wasn't with the project files.

It wasn't with the save operation.

The issue was the behaviour of the embedded browser.

A normal:

```csharp
Browser.Reload();
```

requests a page reload, but does not explicitly tell the browser to ignore its cache.

For a normal website, browser caching is desirable.

For a development environment, however, it can become a source of friction.

WAMP-DS is specifically intended to provide a development workflow, so when a developer saves a CSS file and refreshes the preview, the expectation is that the latest version should be displayed.

---

## The Fix

Rather than clearing the entire WebView2 browsing cache on every save, the refresh operation was changed to explicitly request a reload while ignoring cached resources.

WebView2 provides access to the Chromium DevTools Protocol, which includes a page reload operation with an `ignoreCache` option.

The preview refresh can therefore request:

```csharp
await Browser.CoreWebView2.CallDevToolsProtocolMethodAsync(
    "Page.reload",
    "{\"ignoreCache\":true}"
);
```

The docked preview uses the same approach:

```csharp
await LivePreviewBrowser.CoreWebView2.CallDevToolsProtocolMethodAsync(
    "Page.reload",
    "{\"ignoreCache\":true}"
);
```

This changes the behaviour from a normal browser reload to a development-oriented reload that bypasses cached resources.

---

## Keeping The Preview Refresh Targeted

It would have been possible to clear the entire WebView2 cache whenever the developer saved a file.

However, that would be unnecessarily aggressive.

WAMP-DS previews may contain:

- CSS
- JavaScript
- Images
- Fonts
- PHP output
- Other project resources

Clearing the complete browser cache on every save would potentially discard resources that did not need to be reloaded.

Instead, the refresh operation itself was changed to tell the browser:

    Reload the page
        ↓
    Ignore the cache

This keeps the solution focused on the actual development problem.

The project files themselves are not modified.

The HTML and CSS do not need artificial cache-busting parameters.

The behaviour is contained entirely within WAMP-DS's preview environment.

---

## Integration With Save

The existing save workflow already refreshed the preview after a successful save:

```csharp
if (saved)
{
    previewWindow?.RefreshPreview();

    RefreshDockedPreview();
}
```

This meant the cache problem could be fixed at the preview layer without changing the editor's save behaviour.

The workflow remains:

    Edit File
        ↓
    Ctrl + S
        ↓
    File Saved
        ↓
    Preview Refreshed
        ↓
    Cache Ignored
        ↓
    Latest Changes Visible

This is important because the developer should not have to think about browser caching while working inside WAMP-DS.

---

## Why This Matters

This is not a major headline feature.

There is no new window.

No new toolbar button.

No complicated UI.

But it has a direct impact on the development experience.

A development environment should make the feedback loop between changing code and seeing the result as short and reliable as possible.

If a developer changes:

```css
.container {
    padding: 20px;
}
```

to:

```css
.container {
    padding: 40px;
}
```

then saves the file, the preview should show the new result.

It shouldn't require the developer to start wondering whether the browser has decided to ignore them.

---

## Real-World Testing

This issue was discovered during actual development inside WAMP-DS rather than through a dedicated test case.

That distinction is important.

The application was being used to build and modify a real project.

A small CSS change was made.

The file was saved.

The preview was refreshed.

The expected visual change did not appear.

That immediately exposed a weakness in the existing development workflow.

After identifying the browser cache as the cause and changing the refresh behaviour to ignore cached resources, CSS changes began appearing immediately after saving.

The workflow became predictable again:

    Edit
        ↓
    Save
        ↓
    Preview
        ↓
    See The Change

---

## Result

The live preview now performs a cache-bypassing refresh when WAMP-DS requests a preview update.

This means CSS and other changed resources are reloaded from the development environment rather than relying on previously cached versions.

The important result is not the implementation itself.

It is the removal of a small but surprisingly disruptive piece of friction.

The developer should not have to think about:

> "Why isn't my CSS change showing?"

They should be able to change the code, save it and immediately see the result.

This was another issue that only became obvious through using WAMP-DS for actual development.

It is exactly the sort of problem that can easily disappear into a traditional development process because technically, everything appears to be working.

The file saves.

The browser reloads.

The server responds.

And yet the developer still doesn't see their change.

Now it does.

---

## The Bigger Picture

This is becoming a recurring theme in the development of WAMP-DS.

The larger features are important, but some of the most valuable improvements are the small ones that remove friction from the development loop.

Find and Replace removed unnecessary navigation.

`Ctrl+D` removed unnecessary copy and paste operations.

The preview cache fix removes unnecessary confusion when checking CSS and other resource changes.

None of these features fundamentally changes what a developer can build.

They change **how much effort is required to build it**.

That is increasingly becoming an important part of what WAMP-DS is trying to achieve.

The goal isn't simply to provide Apache, PHP, MySQL, an editor and a preview.

The goal is to make the entire workflow feel immediate.

Edit.

Save.

See the result.

No unnecessary friction.

No wondering whether the application actually did what was asked.

Just development.
